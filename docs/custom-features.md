# Custom features that need admin setup

Features whose theme code is in place but that do nothing until they are configured in the
Shopify admin.

## 1. Tagging orders with the theme Rollouts served

Rollouts does not expose which theme a customer was served, and a theme cannot tag an order, so
the theme id travels with the cart and Flow turns it into a tag.

- `assets/theme-ab-attribute.js` writes the id of the theme rendering the page to the
  `_theme_ab` cart attribute, on page load, once per cart (first write wins).
- The attribute reaches the order as a custom attribute.
- A Flow on **Order created** reads it and adds the tag.

### Flow setup

1. Find the id of each theme in the Rollout: **Online Store → Themes**, open the theme
   customizer, and take the number from the url (`/admin/themes/<id>/editor`).
2. Create a Flow: trigger **Order created**.
3. Condition — **Order → Custom attributes**, key `_theme_ab`, value equals the id of theme A.
4. Action — **Add order tags**, e.g. `Theme A`.
5. Add an `Otherwise` branch with the id of theme B and its own tag.

### What this does not cover

- Orders that never go through the storefront carry no attribute: draft orders, subscription
  renewals, POS. Give the Flow a branch for a missing attribute rather than assuming A or B.
- A customer served theme A who is later served theme B keeps the A attribute, because the cart
  was built on A. Change `theme-ab-attribute.js` if last write should win instead.
- The attribute shows in the order's **Additional details**. Confirm during testing whether the
  underscore prefix hides it at checkout, and rename it if merchants should not see it.

## 2. Hiding variants from the storefront

Two levels, for two different asks:

- **Hide single variants**, leaving the option in place — `snippets/variant-hidden.liquid` decides
  whether a variant is shown, `snippets/variant-visible-values.liquid` turns that into the option
  values a picker renders, and `snippets/variant-visible-selected.liquid` into the variant a
  picker starts on.
- **Hide a whole option**, label and all — `snippets/variant-option-hidden.liquid`.

### Metafield definitions

| Owner   | Namespace and key        | Type                     | Purpose                                     |
| ------- | ------------------------ | ------------------------ | ------------------------------------------- |
| Variant | `custom.variant_hidden`  | Boolean                  | Hide this one variant                       |
| Product | `custom.hidden_variants` | List of single line text | Hide these option values or variant titles  |
| Product | `custom.hidden_options`  | List of single line text | Hide these whole options, label included    |

`custom.hide_variant_option`, the comma separated list the new Mahalo picker shipped with, is
still read, so products already configured with it keep working. Use `custom.hidden_variants` for
anything new.

Entries match ignoring case and spaces: `3pack-16oz` matches the variant `3 Pack - 16oz`. An
entry can name a whole option value, so `["16oz"]` on a Flavor × Size product hides every 16oz
variant and takes `16oz` out of the Size picker.

`hidden_options` names options rather than values: `["Size"]` takes the `Size:` label and all of
its buttons off the page in one go. The variant is still chosen — the picker keeps the selected
value in an input that is never shown, so the option resolves and the product stays buyable — the
customer just has no say in it. That makes it worth using only when every value of the option
would be hidden anyway; to drop some values and keep the rest, use `hidden_variants`.

### Where it applies

Product page pickers (`variant-main-picker`, `variant-main-picker-new-mahalo`,
`variant-flavor-carousel`), quick add (`variant-quick-add`), product card swatches
(`variant-swatches`), the card link (`product-card`, `product-card-variant-url`) and the
hydration flavor grid (`variant-picker-hydration`).

`hidden_options` applies to the product page pickers, quick add and card swatches. On a card the
option is dropped outright, with no input left behind, the way a swatchless option already is.

### What this does not cover

- **A hidden variant is still purchasable.** Hiding is storefront markup only: the Storefront API
  and a hand written `/cart/add` request still reach it. Unpublish or archive the variant to stop
  it from being sold, or add a cart validation function.
- **One combination of a multi option product.** An option value disappears only when every
  variant carrying it is hidden, so that hiding `Vanilla / 16oz` does not take `Vanilla` away
  while `Vanilla / 8oz` is still for sale. Hiding a single combination of a multi option product
  needs the picker to disable combinations, which it does not do today.
- **Sections generated by PageFly and Replo** (`sections/pf-*`, `snippets/pf-*`,
  `snippets/reploChunk.*`) render their own variant markup and ignore these metafields.
- **A variant already in someone's cart** stays there.
- Hiding every value of an option is treated as a misconfiguration: the option is rendered whole,
  so the product never becomes impossible to buy.

## 3. Pre-order products

`snippets/pre-order.liquid` decides whether a product is on pre-order and what it says.
`snippets/add-to-cart-button.liquid` relabels the button and `blocks/buy-buttons.liquid` prints
the note under it.

The label is read from the product in the snippet that prints it, rather than handed down as
`add_to_cart_text` from `buy-buttons`, so that nothing between the two can drop it. The
`custom.sold_out` handling already in that snippet works the same way.

Two things rewrite that button text after the page renders, so the label needs defending:

- `sections/new-product-information.liquid` appends the variant price on the Mahalo templates. It
  reads the label from `data-base-label` on the text element, so it appends the price to
  `Pre-Order` rather than replacing it with `Add To Cart`.
- The **Recharge subscription widget** replaces the text outright, from outside the theme. On a
  pre-order button only, `assets/pre-order-label.js` watches for that and puts the label back,
  keeping any price suffix. Ordinary products load nothing and are left alone.

If the button ever reverts again, compare the visible text with `data-base-label` on
`.add-to-cart-text__content`: the two differing means something is still overwriting it, the two
matching on the wrong words means the Liquid never resolved.

### Metafield definitions

| Owner   | Namespace and key        | Type             | Purpose                                     |
| ------- | ------------------------ | ---------------- | ------------------------------------------- |
| Product | `custom.pre_order`       | Boolean          | Put this product on pre-order                |
| Product | `custom.pre_order_text`  | Single line text | Override the note for this product only      |

With `custom.pre_order` false or unset, the product behaves exactly as before.

### Customizer settings

**Online Store → Customize → Theme settings → Pre-order**:

- **Button text** — what the add to cart button says, `Pre-Order` by default.
- **Note under the button** — the line under it, `This item is on pre-order and will be shipped
  on [add date]` by default. Replace `[add date]` with the ship date. Leave it empty to show no
  note at all.

These are theme settings rather than block settings because every product template carries its
own buy buttons block, and a store wide message should not have to be retyped fourteen times.
A single product still overrides the note through `custom.pre_order_text`.

### What this does not cover

- **Sold out wins.** A variant that cannot be added to the cart keeps its `Sold out` button and
  shows no note: there is nothing to pre-order. A pre-order product therefore needs its inventory
  set to continue selling when out of stock.
- **Quick add shows the label too, but never the note.** Quick add renders the same button
  snippet, so a pre-order product says `Pre-Order` there as well; the note only exists on the
  product page.
- **`custom.sold_out` wins over everything.** A product with that metafield set keeps its
  hardcoded `Out of Stock` button.
- **Nothing downstream changes.** The cart, checkout and order still treat the line as an ordinary
  purchase; the note is wording, not a fulfilment hold.

## 4. Automatic discounts in the purchase options fieldset

The Yagi Automatic Discount app mirrors a Shopify automatic discount into metafields so the
storefront can show the discounted price before the cart. `snippets/auto-discounted-price.liquid`
uses them for product cards. The subscribe / one-time fieldset on the Mahalo templates cannot:
the discount applies to the cart line, so it is in neither `variant.price` nor a selling plan
allocation, and the fieldset is the only price a customer sees on those templates — they carry no
theme price block and no app block.

- `snippets/auto-discount-price-value.liquid` discounts one price and outputs it in cents, or
  nothing when no discount is running. A value rather than markup, so a caller can format it the
  way it already formats prices — and so it works on a selling plan allocation, which a product
  level snippet cannot see.
- `snippets/new-purchase-options-new-mahalo.liquid` and `snippets/purchase-options-mahalo.liquid`
  use it for both rows, and for the per variant price map the sync script reads.
- `snippets/variant-main-picker-new-mahalo.liquid` puts the discounted prices in the
  `data-variant-*-price-text` attributes, because `snippets/purchase-options-sync.liquid` prefers
  those over the map and would otherwise put the undiscounted price back on the first variant
  change.
- The strikethrough on the subscribe row is what the variant costs without a subscription, so it
  follows the one-time price down only when the discount reaches the subscription too. A
  subscription at its full price struck through with a lower one-time price would read as the
  more expensive option. It travels as `subCompare` in the price map and
  `data-variant-sub-compare-price-text` on the picker.

- The `21% OFF` / `25% OFF` chip on the variant buttons is gone with them. It was a percentage
  hardcoded per variant title in `variant-main-picker-new-mahalo.liquid`, derived from those
  same list prices, so once they went it stated a saving against nothing. A real saving reaches
  a variant button through `variant-badges` and its metafields instead.

- The one-time row shows one price, the one the customer is charged. The only thing struck
  through beside it is a saving that exists: a `compare_at_price` set on the variant in the
  admin, or, with a discount running, the price the discount was taken off, so the two numbers
  match the cart line. The list prices the snippets used to hardcode per variant title (`1 -
  16oz` compared against $34, `3 Pack - 16oz` against $102, and $78 / $156 for daily greens in
  `variant-main-picker-new-mahalo`) were removed: they were not what anyone is charged, so the
  row struck through a number the customer sees nowhere else. To strike a price through again,
  set the variant's compare at price in the admin.

- The subscribe row reads as one phrase, "Subscribe & Save 20%": the title carries the words
  and the badge beside it carries the number alone. On the Mahalo template the badge is the
  section setting **Discount badge**, `[discount]%`; wording it `Save [discount]%` again makes
  the row say save twice. The badge inherits the title's font size rather than setting its own,
  so the row keeps its height at every breakpoint.

- The one-time row carries a `Save X%` badge while a discount is running, the counterpart of the
  subscription badge next to it. The percentage is derived from the two prices rather than read
  off the metafield, so it always states the saving the row shows. On the Mahalo template the
  wording is a section setting, **One-time discount badge**, next to the one it mirrors; on
  new-Mahalo it is hardcoded with the rest of that fieldset copy.

With no discount running, every price is exactly what it was before, list prices included, and
no badge is rendered.

### Where the numbers come from

Nothing in the Mahalo fieldset is a figure typed into the theme. Every number is read from the
product:

| Shown | Read from |
| ----- | --------- |
| The subscribe badge and `[discount]` in the benefits | the percentage `price_adjustment` on the product's selling plan |
| The subscription price | the variant's `selling_plan_allocation` for that plan |
| The one-time price and anything struck through | `variant.price` and `variant.compare_at_price` |
| The `Save X%` badge on the one-time row | the two prices the row itself shows |
| The frequency options | the selling plan names |
| Variant names in the picker | `custom.variant_label` / `custom.variant_labels`, through `variant-label.liquid` |

What is written in the theme is copy, and all of it is a section setting a merchant can reword:
the titles, the benefit lines and the badges. The strings in the Liquid are only the defaults
those settings start from.

Two scripts do carry a hardcoded percentage — `sections/product-information.liquid` rewrites
`5.88%` to `20%` inside the widget, and `assets/hydrate-pdp.js` writes `Save 20%` over its badge.
Both exist to correct the Recharge widget on the templates that show it, and neither runs on
Mahalo: the section does not render its script there at all, and `hydrate-pdp.js` stops as soon
as it finds the widget hidden. A Mahalo page therefore has no invented figure on it.

**Known gap:** the subscribe badge reads the first selling plan of the first group, so a product
whose plans carry different percentages states the first one whatever frequency the customer
picks. Products with one percentage across their plans are unaffected.

### Admin setup

**Discounts → the automatic discount → Purchase type** decides whether the discount reaches a
subscription line, and the app does not sync that field: its metafields carry the percentage and
the products, but nothing that says which purchase type earns it. Every other fact the theme
needs is already synced, so rather than restating a campaign in the theme, only that one missing
field is kept in the shop metafield **`custom.auto_discount`**:

| Owner | Namespace and key      | Type | Purpose                                     |
| ----- | ---------------------- | ---- | ------------------------------------------- |
| Shop  | `custom.auto_discount` | JSON | What the running automatic discount applies to |

```json
{ "purchase_type": "one_time" }
```

`purchase_type` is `one_time`, `subscription` or `both`, matching the Purchase type on the
discount. **It has to be changed whenever a campaign with a different purchase type goes live.**

Unset, or set to anything else, is read as `one_time`. That is the safe end of the mistake: a
discount that goes unadvertised costs a conversion, a subscription that quietly costs more at
checkout than the page promised costs the order and the trust.

Shop metafields are not part of the theme, so both themes in a Rollout read the same value and
nothing has to be set twice.

### What this does not cover

- **Recurring subscription orders.** A Shopify automatic discount applies to the order placed
  through checkout. Renewals are created by Recharge, which has its own discounts, so the second
  order onwards is charged the ordinary selling plan price.
- **Fixed amount discounts.** Only `discount_percentage` can be applied to a price the theme
  chooses; `min_auto_discounted_price` is one number for the whole product, so it cannot give a
  per variant or a per selling plan price. A fixed amount discount shows nothing in the fieldset
  and is applied at the cart as usual.
- **Two campaigns at once with different purchase types.** `custom.auto_discount` is one value
  for the whole shop, and the app metafield is one percentage per product, so neither layer can
  tell two overlapping discounts apart. Running a one-time only discount alongside a subscription
  one needs the metafield to grow a list scoped by collection, and the snippet to pick from it.
- **Combining with other discounts** is decided by the discount itself, not the theme. The theme
  shows one percentage.
- **The theme price block on other templates.** `snippets/price.liquid` deliberately leaves the
  main product price alone, because the app's own block renders it. A template without that block
  shows the undiscounted price.
